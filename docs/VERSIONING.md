# Версионность

- Старт: 0.0.0 — инициализация.
- Каждое завершённое изменение — отдельная микроверсия и запись в CHANGELOG.
- Нумерация: 0.0.1 … 0.0.99 → 0.1.0; 0.99.99 → 1.0.0. Если крупная незавершённая задача пересекла границу, промежуточные микрошаги допускаются до фактического завершения; релизная граница фиксируется явно.
- Коммиты и релизные записи описывают смысл изменений на русском языке.
- Теги релизов: vX.Y.Z. Не передвигать опубликованные теги; при ошибке выпускать новую версию.
- VERSION и CHANGELOG должны совпадать с текущей версией. Наличие записи не заменяет фактическую проверку тега.
- Изменения проверять до интеграции; для последующих работ предпочтительны pull request и squash merge.

## Автоматическое обслуживание

Workflow `Repository maintenance` запускается после успешного push-CI основной ветки, ежедневно и вручную. Использует только временный встроенный GITHUB_TOKEN с правом contents: write в выделенной задаче; PAT, личные токены и обход rulesets не требуются. Код запускается исключительно из доверенного main, а не из PR.

- Исторические теги до 0.0.12 проверяются по явному реестру коммитов main. Только точный корневой коммит v0.0.0, созданный до появления VERSION, проверяется по SHA, положению в истории и заголовку. Для всех последующих версий обязателен VERSION. Новые теги создаются только для уникального увеличения VERSION с соответствующим заголовком коммита и успешным push-CI на конкретном SHA. Существующие теги никогда не обновляются и не удаляются.
- Нативное Automatically delete head branches остаётся включённым. Дополнительная очистка проверяет только ветки feature/, design/, qa/, fix/, docs/, chore/, release/ из этого репозитория, закрытые PR в main, отсутствие открытого PR, неизменившийся SHA и совпадение дерева с интегрированным коммитом. Для закрытого без статуса merged PR требуется также совпадение исходной базы с родителем коммита main. Удаление защищено lease на SHA. Main, защищённые ветки, форки и непроверенные ветки исключены.
- Перед слиянием PR workflow не имеет прав записи; модульные тесты проверяют решение на синтетических данных. Реальное применение подтверждается журналом workflow и проверкой refs.
- Повторный запуск безопасен: существующие корректные теги и уже удалённые ветки не изменяются. Ошибки не обходятся ослаблением защиты. Ручной запуск: Actions → Repository maintenance → Run workflow (main).

Ограничение: push тегов встроенным GITHUB_TOKEN не запускает другие tag-triggered workflows; при появлении таких релизных процессов потребуется отдельный доверенный workflow/dispatch. Автоматизация не создаёт GitHub Releases.
